# 01. 제품 기획 — 무엇을, 누구를 위해, 어디까지 만드는가

> 이 문서의 모든 결정에는 **"왜"** 가 붙어 있다. 면접에서 "왜 이렇게 했어요?"라는 질문에 이 문서가 곧 답이다.
> 원칙: **업계 표준을 따른다.** 표준에서 벗어난 곳은 이유와 함께 [08-cost-and-limits.md](08-cost-and-limits.md)에 모아 둔다.

## 1. 한 줄 정의

**여러 회사(테넌트)가 각자 직원의 필수 교육을 배정하고 수료 현황을 추적하는 B2B SaaS형 사내교육 LMS.**

### 왜 "B2B 사내교육"인가
면접 볼 회사가 만들려는 LMS가 기업 사내교육(B2B)이다. B2C 강의 플랫폼과는 핵심이 다르다.

| 구분 | B2C 강의 플랫폼 | **B2B 사내교육 (우리)** |
|---|---|---|
| 돈 내는 사람 | 수강생 본인 | **회사** (HR·교육 담당) |
| 수강 시작 | 학습자가 골라서 결제 | **회사가 배정**(필수 교육, 마감일) |
| 핵심 화면 | 강의 목록, 결제, 리뷰 | **관리자 대시보드**(누가 안 들었나) |
| 핵심 기술 과제 | 결제, 검색, 추천 | **조직 데이터 격리, 기업 로그인(SSO), 권한, 감사 로그, 학습 기록 표준(xAPI)** |
| 가입 | 누구나 회원가입 | **관리자 초대** 또는 **회사 SSO** |

### 왜 "멀티테넌트 SaaS"인가
- 초기 스타트업은 고객사마다 설치해주는 구축형보다 **하나의 서비스를 여러 고객사가 같이 쓰는 SaaS**로 시작하는 게 일반적이다. 운영 인력이 적기 때문이다.
- 가장 큰 위험은 **"A회사 직원이 B회사 데이터를 보는 사고"** 다. 이걸 어떻게 막았는지가 백엔드 역량을 가장 선명하게 보여준다.

## 2. 사용자 모델 — 전역 사용자 + 회사별 멤버십 (업계 표준)

```
User(사람 1명, 전역)  ──<  Membership(회사별 소속, 역할, 부서)  >──  Tenant(회사)
```

| 개념 | 의미 | 예 |
|---|---|---|
| **User** | 로그인하는 사람. 전 서비스에서 1명 | 외부 강사 박두리 |
| **Tenant** | 고객사 | ACME, 베타전자 |
| **Membership** | "이 사람이 이 회사에서 어떤 역할인가" | 박두리 @ ACME = 강사, 박두리 @ 베타전자 = 강사 |

**왜 이 구조인가 (Slack, Notion, GitHub가 모두 이 구조다)**
- 외부 강사, 컨설턴트, 계열사 겸직자처럼 **한 사람이 여러 회사에 속하는 경우**가 B2B에서 흔하다.
- 처음에 "1인 1회사"로 만들면, 나중에 바꿀 때 인증과 데이터 전체를 뜯어고쳐야 한다. **설계 단계가 바꾸기 가장 싼 시점**이다.
- 역할이 사람이 아니라 **멤버십에 붙는다.** 같은 사람이 A회사에서는 관리자, B회사에서는 학습자일 수 있다.

### 역할 (Membership.role)

| 역할 | 누구 | 하는 일 | 왜 따로 필요한가 |
|---|---|---|---|
| **ORG_ADMIN** | HR, 교육 담당자 | 회사 설정, 부서, 직원 초대, SSO 설정, 교육 배정, 현황 | 돈을 내고 결과를 보고하는 사람 |
| **INSTRUCTOR** | 사내 강사, 외부 강사 | 코스, 레슨, 퀴즈 제작 | 콘텐츠 담당이 전 직원 개인정보를 볼 이유는 없다 (최소 권한 원칙) |
| **LEARNER** | 직원 | 배정된 교육 수강, 퀴즈, 수료증 | 대부분의 사용자. 자기 데이터만 본다 |

> 역할을 3개로 제한한 이유: 역할이 늘면 권한 조합이 기하급수로 늘어난다. "부서장은 자기 부서만 보기"는 확장 기능으로 남긴다.

## 3. 로그인 — 이메일 우선 로그인 (Identity-first, 업계 표준)

1. 사용자가 **이메일만** 먼저 입력한다.
2. 이메일 도메인(`@acme.com`)이 **SSO를 설정한 회사의 도메인이면 그 회사의 로그인 화면**(구글 워크스페이스, Okta, Entra ID 등)으로 자동 이동한다.
3. 아니면 비밀번호(+ 관리자는 2단계 인증) 화면을 보여준다.
4. 로그인한 사람이 여러 회사에 속해 있으면 **회사 선택** 화면을 보여준다(Slack 워크스페이스 전환과 같다).

**왜 이 방식인가**
- "회사 코드를 입력하세요"는 사용자가 코드를 기억해야 하는 옛날 방식이다. 이메일은 누구나 안다.
- 기업 고객은 **"우리 회사 계정으로 로그인(SSO)"** 을 거의 필수로 요구한다. 이메일 도메인으로 회사를 찾는 방식이 SSO와 자연스럽게 이어진다.
- 이 흐름 전체를 **Keycloak**(오픈소스 인증 서버)의 Organizations 기능이 제공한다. 우리가 로그인 화면과 비밀번호 저장을 직접 만들지 않는다([02](02-tech-decisions.md) B6).

## 4. 핵심 시나리오

1. **회사 등록**: HR 담당 김하나가 회사명 `ACME`, 회사 이메일 도메인 `acme.com`으로 등록한다. 김하나는 ACME의 첫 ORG_ADMIN이 된다.
2. **조직 구성**: 김하나가 부서(개발팀, 영업팀)를 만들고 직원을 초대한다. 직원은 초대 메일 링크로 계정을 만든다.
3. **(선택) SSO 연결**: 김하나가 회사 IdP를 연결하면, 이후 `@acme.com` 직원은 회사 계정으로 바로 로그인한다.
4. **콘텐츠 제작**: 강사 박두리가 「정보보안 기초」 코스를 만들고, 레슨(영상, 문서, 텍스트)과 최종 퀴즈(통과 기준 70점)를 붙인다. 아이폰으로 찍은 영상(.mov, 1.2GB)을 올리면 **분할 업로드**되고, 서버가 **여러 화질의 스트리밍용 영상으로 변환**한다. 변환이 끝나면 게시한다.
5. **교육 배정**: 김하나가 이 코스를 **전 부서**에 이번 달 말까지 배정한다. → 해당 직원 전원에게 수강이 생기고 알림 메일이 나간다.
6. **학습**: 이세나가 영상을 보면 진도가 저장되고, 학습 행동이 **xAPI 기록**("이세나가 레슨 3을 완료했다")으로 남는다.
7. **수료**: 퀴즈를 80점으로 통과하면 **자동 수료**되고, 수료증 PDF가 비동기로 발급된다.
8. **현황 확인**: 김하나가 대시보드에서 부서별 수료율, 미이수자, 마감 임박자를 보고 리마인더를 보낸다.
9. **신규 입사자**: 개발팀에 새로 들어온 직원에게 개발팀에 걸린 배정이 **자동으로** 생긴다.

## 5. LMS 업계 표준과의 관계

| 표준 | 무엇인가 | 이번 범위 | 이유 |
|---|---|---|---|
| **xAPI** (Experience API) | "누가 · 무엇을 · 했다" 형식의 학습 기록 표준. 기록 저장소는 LRS | ✅ **적용** | 학습 기록을 표준 형식으로 남기면 외부 LRS나 분석 도구로 그대로 내보낼 수 있다. 비용 0원, 설계만 맞추면 된다 |
| **SCORM** 1.2 / 2004 | 저작 도구(Articulate 등)로 만든 콘텐츠 패키지 규격. 기업 교육 콘텐츠 유통의 사실상 표준 | 📄 문서로만 | 패키지 업로드, 압축 해제, 동일 출처 서빙, 런타임 API 구현이 필요해 5일 안에 불가. "다음 단계 1순위"로 명시 |
| **cmi5** | xAPI 기반의 SCORM 후속 규격 | 📄 문서로만 | xAPI 기록 구조를 맞춰 두면 이후 도입이 쉽다 |
| **LTI 1.3** | 외부 학습 도구(실습 환경, 화상 강의)를 LMS에 끼워 넣는 연동 규격 | 📄 문서로만 | 연동할 외부 도구가 있어야 의미가 있다 |
| **HLS** + 서명 쿠키 | 영상 스트리밍 표준 (여러 화질, 네트워크에 맞춰 자동 전환) | ✅ **Should** | 원본을 그대로 주면 재생 호환성(아이폰 HEVC), 트래픽, 버퍼링 문제가 생긴다. MediaConvert로 변환([02](02-tech-decisions.md) B16-2) |

### 한국 사내교육 시장의 맥락 (면접 전에 확인할 것)
- 국내 사내교육은 **법정의무교육**(성희롱 예방, 개인정보보호, 산업안전 등)과 **고용보험 환급과정**(HRD-Net) 비중이 크다.
- 환급과정에는 본인 인증, 진도 관리, 대리 수강 방지 같은 별도 요건이 따라오는 것으로 알려져 있다(정확한 요건은 미확인).
- **→ 면접 볼 회사가 이 시장을 노리는지 미리 알아보면 가장 강력한 질문거리가 된다.** 이번 MVP는 기능적으로 대응하지 않고 [08](08-cost-and-limits.md)에 "할 수 없는 것"으로 정리한다.

## 6. 기능 범위 — MoSCoW (5일 유지, 범위 축소)

> Spring을 새로 익히면서 업계 표준 인프라까지 올려야 하므로 **기능은 줄이고 깊이를 지킨다.**

### Must (5일 안에 반드시)
| 기능 | 왜 Must인가 |
|---|---|
| Keycloak 로그인 (이메일 우선, BFF 세션) | 모든 기능의 전제. 표준 인증 구조의 증거 |
| **멀티테넌트 격리** (Hibernate `@TenantId` + Postgres RLS) | 이 프로젝트의 정체성 |
| 멤버십 기반 RBAC | B2B 필수 |
| 회사 등록, 부서, 직원 초대 | B2B 가입 흐름 |
| 코스 → 섹션 → 레슨, **S3 Multipart 업로드** | 콘텐츠. 강의 영상은 수백 MB~수 GB라 분할 업로드가 표준 |
| 교육 배정 (부서·개인, 마감일) | B2B LMS의 핵심 차별점 |
| 진도 (레슨 완료, 영상 시청) + **xAPI 기록** | 학습 관리의 본체, LMS 표준 |
| 퀴즈 자동 채점 → 수료 | 결과물 |
| 관리자 대시보드 (부서별 수료율, 미이수자) | 돈 내는 사람의 화면 |
| Storybook (핵심 컴포넌트) | 디자인 시스템 |
| **Terraform으로 AWS 배포, CI/CD** | 현업 인프라의 증거 |

### Should
| 기능 | 이유 |
|---|---|
| 수료증 PDF (아웃박스 → SQS → 워커) | 비동기 처리 표준 패턴을 보여주는 좋은 소재 |
| 감사 로그 | 보안 감사 대응, 개인정보 접속기록 |
| 초대·배정·리마인더 메일 (SES) | |
| 관리자 2단계 인증 (Keycloak OTP) | 설정만으로 가능 |
| SSO 시연 (Keycloak 렐름 하나를 "고객사 IdP"로 꾸밈) | B2B 핵심 요구를 실제로 보여줌 |
| 신규 입사자 자동 배정 | 시나리오 9 |
| **영상 변환 (MediaConvert → HLS 여러 화질, 썸네일, 서버가 정한 영상 길이)** | 재생 호환성과 트래픽 문제의 표준 해법. 아웃박스 → SQS → 워커 흐름을 재사용. 밀리면 "H.264 mp4만 허용 + 원본 재생"으로 후퇴 |

### Could
- Playwright E2E 추가, k6 부하 테스트, 스테이징 환경 실제 배포, 업로드 파일 악성코드 검사

### Won't (이번엔 안 함 — 이유를 설명할 수 있어야 함)
| 기능 | 이유 | 나중에 한다면 |
|---|---|---|
| SCORM 패키지 재생, LTI | §5 참고 | SCORM 런타임 오픈소스 + 동일 출처 콘텐츠 서빙 |
| SCIM 직원 자동 동기화 | 고객사 IdP(Okta, Entra ID) 환경이 필요 | SCIM 2.0 엔드포인트 |
| 결제, 구독 | B2B는 계약 후 인보이스가 일반적 | Stripe, 토스페이먼츠 |
| 영상 DRM, 휴대폰 본인인증, HRD-Net 연동 | 유료 계약 또는 승인 기관만 가능 | [08](08-cost-and-limits.md) |
| 서브도메인 테넌트 (`acme.lms.com`) | 이메일 우선 로그인으로 대체 | 와일드카드 인증서 + 테넌트 브랜딩 |
| 모바일 앱 | 반응형 웹으로 대체 | API를 그대로 재사용 (Bearer 토큰 API) |

## 7. 화면 목록 (IA)

```
[공개]
  /                        랜딩
  /signup                  회사 등록 (회사명, 이메일 도메인, 관리자 정보)
  /login                   → Keycloak 로그인 화면으로 이동 (이메일 우선)
  /verify/[serial]         수료증 진위 확인

[공통]
  /select-org              소속 회사 선택 (여러 회사에 속한 경우)

[학습자]
  /app                     내 필수 교육 (진행 중 / 마감 임박 / 완료)
  /app/courses/[id]        코스 상세
  /app/learn/[lessonId]    레슨 학습
  /app/quiz/[quizId]       퀴즈
  /app/certificates        내 수료증

[강사]
  /app/studio              내 코스
  /app/studio/[id]         코스 편집 (섹션·레슨 정렬, 업로드, 퀴즈)

[관리자]
  /app/admin               대시보드
  /app/admin/members       멤버, 초대, 역할 변경
  /app/admin/departments   부서
  /app/admin/assignments   교육 배정
  /app/admin/sso           SSO 설정 (Should)
  /app/admin/audit         감사 로그 (Should)
```

> 프론트의 라우트 보호는 UX일 뿐이다. **보안 경계는 항상 API**다.

## 8. 성공 기준 (면접 당일의 "완성")

- [ ] 면접관이 `app.도메인`에 접속해 **데모 계정 3개**(관리자·강사·학습자)로 시나리오 1~8을 해볼 수 있다.
- [ ] **A회사 멤버의 토큰으로 B회사 데이터를 요청하면 차단되는 것**을 테스트 코드로 증명한다.
- [ ] 학습 행동이 xAPI 형식으로 기록되는 것을 보여준다.
- [ ] GitHub README에 아키텍처 그림, 기술 선택 이유, 비용, 실행 방법이 있다.
- [ ] Storybook(Chromatic) 링크로 디자인 시스템을 볼 수 있다.
- [ ] main에 머지하면 CI → ECR → ECS로 자동 배포되고, 실패하면 자동 롤백된다.
- [ ] `terraform apply`로 인프라 전체가 만들어지고 `terraform destroy`로 지워진다.
- [ ] 노트북에서 `docker compose up`으로 전체가 뜬다 (AWS 장애·과금 문제 대비 백업 시연).
