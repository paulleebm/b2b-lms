# 디자인 검토 기준

UI가 바뀌는 PR은 이 기준을 통과해야 머지한다. 출처는 open-design `critique`(5개 관점 점수), Impeccable `critique`·`audit`, open-design `craft` 규칙, Vercel Web Interface Guidelines다. 기준 문서는 [DESIGN.md](../../DESIGN.md).

## 1단계 — 기계적 검사 (CI, 자동)

| 검사 | 도구 | 기준 |
|---|---|---|
| 토큰 대비 | `pnpm --filter @lms/ui check:contrast` | 글자 4.5:1, UI 경계 3:1 (DESIGN.md §2의 모든 짝) |
| 접근성 위반 | Storybook a11y 애드온(axe), 스토리 테스트 | 위반 0건 |
| 인터랙션 | Storybook `play` 함수 (Vitest) | 전부 통과 |
| 타입·린트·빌드 | `pnpm -r typecheck`, `lint`, `build-storybook` | 통과 |

## 2단계 — 체크리스트 (리뷰어가 Storybook에서 확인)

**상태** (craft/state-coverage)
- [ ] 데이터를 보여주는 모든 컴포넌트에 로딩 · 빈 상태 · 오류 · 정상 · 극단값 스토리가 있다
- [ ] 빈 상태에 제목 + 이유 + 다음 행동이 있다. 오류에 무슨 일 → 이유 → 행동이 있다
- [ ] 인터랙티브 컴포넌트에 hover · focus-visible · active · disabled · loading이 있다

**접근성** (craft/accessibility-baseline, `accessibility` 스킬)
- [ ] 키보드만으로 모든 동작이 가능하고 포커스가 항상 보인다
- [ ] 상태가 색만이 아니라 아이콘 + 글자로 전달된다
- [ ] 차트에 같은 데이터의 표가 있다
- [ ] 폼: 라벨 연결, `aria-describedby`, `aria-invalid`, 첫 blur 이후 검증

**디자인 계약** (DESIGN.md)
- [ ] 토큰에 없는 색을 쓰지 않았다 (`#6366f1` 같은 기본 인디고 금지)
- [ ] 강조색(`--accent`)이 화면당 2곳 이하
- [ ] 인장(`--seal`)이 수료·수료증에만 쓰였다
- [ ] 한글 제목 행간 1.3~1.4, 본문 1.7~1.8, 한글에 음수 자간 없음
- [ ] 숫자에 `tabular-nums`, 숫자 열 오른쪽 정렬

**AI 디자인 징후** (anti-ai-slop, Impeccable craft-floor, Anthropic frontend-design)
- [ ] 제목 위 영문 대문자 꼬리표가 없다
- [ ] 같은 크기 카드 격자, 카드 안 카드가 없다
- [ ] 색 있는 왼쪽 테두리(1px 초과)가 없다
- [ ] 이모지·유니코드 기호 아이콘이 없다. 버튼 글자 뒤 `→`가 없다
- [ ] 지어낸 수치, 채우기 문구가 없다. 데모 데이터는 "합성 데이터"로 표시했다

## 3단계 — 5개 관점 점수 (open-design critique)

각 관점을 0~10으로 매기고 **반드시 근거를 쓴다.** 근거 없는 점수는 무효다.

| 관점 | 질문 | 통과선 |
|---|---|---|
| **1. 방향 일관성** | 모든 세부 결정(셸, 색, 간격, 인장)이 "인장과 이수증" 하나를 따르는가? | 7 |
| **2. 시각 위계** | 처음 보는 사람이 무엇을 먼저, 다음에 읽을지 아는가? 관리자는 3초 안에 처리할 사람을 찾는가? | 7 |
| **3. 디테일** | 정렬, 행간, 숫자 기준선, 빈칸, 긴 글자에서 흐트러짐이 없는가? | 7 |
| **4. 기능성** | 작업을 실제로 끝낼 수 있는가? 키보드, 좁은 화면, 극단값에서도? | **8** |
| **5. 독창성** | 다른 SaaS와 구별되는 순간이 있는가? (업무 도구는 5여도 괜찮다) | 5 |

**점수 규율**
- **가장 약한 구간이 점수다.** 두 화면이 좋고 한 화면이 깨졌다면, 깨진 화면 기준으로 매긴다
- **점수를 부풀리지 않는다.** 7은 "괜찮다"가 아니라 "강하다"다. 전부 7 이상이면 비판적으로 보지 않은 것이다
- **업무 도구의 절제는 감점이 아니다.** 독창성은 인장 하나로 충분하다

**보고 형식**
```
관점: 디테일 — 6/10
근거: 대시보드 표의 숫자 열이 왼쪽 정렬이라 자릿수 비교가 안 된다. 긴 부서명(40자)에서 셀이 두 줄로 터진다.
유지: 요약 띠의 세로선 구분
고칠 것: 숫자 열 오른쪽 정렬 + tabular-nums, 부서명 말줄임 + title
빠른 개선: StatStrip 비교 문구 색을 muted로
```

## 검토를 돌리는 방법 (프로젝트에 설치된 스킬)

| 목적 | 명령 | 비고 |
|---|---|---|
| UX 휴리스틱 점수 + 개선안 | `/impeccable critique <대상>` | 바이너리 없이 문서 모드로 동작 (`.claude/skills/THIRD_PARTY.md`) |
| 접근성·성능·반응형 기술 점검 | `/impeccable audit <대상>` | |
| 출시 전 마감 손질 | `/impeccable polish <대상>` | |
| 규칙 기반 UI 리뷰 (`file:line` 형식) | `/web-design-guidelines <파일>` | Vercel 가이드라인을 그때그때 받아옴 |
| WCAG 2.2 점검 | `/accessibility` | |
| 시각 방향 점검 | `/frontend-design` | 새 화면을 시작할 때 |

검토 결과는 PR 설명에 3단계 표와 함께 붙인다.
